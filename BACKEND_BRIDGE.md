# Мост к сайту farlandsconnect — статус и план

Справочник по интеграции UnityLauncher (MySQL, источник истины для игры) с
backend'ом нового сайта `farlands.in` (Postgres, отдельная БД). Механизм —
`auth/FarLandsApiClient.java`: fire-and-forget HTTP-мост, после локальной
мутации в MySQL дублирует событие на `farlands.frammy.lat` через `/plugin/*`.
Подробнее про сам клиент — в `README.md` → «Интеграция» → «Мост с сайтом».

Статус (2026-08-03): протестировано вживую на dev-сервере (Hostinger MySQL) —
регистрация нового игрока (`TheChunky`) реально создала `User` в Postgres
(`POST /plugin/users` → `200`), last-seen пишется на выход (`200`). Прод-MySQL
будет на Apex Hosting — сам мост от выбора хостинга MySQL не зависит, меняется
только `db.properties`. Баланс/транзакции подключены следом (см. «Сделано»).

## Сделано

- [x] `FarLandsApiClient` — HTTP-клиент, `secrets.properties`-конфиг
      (`backend.apiBaseUrl` / `backend.apiToken`), выключен если пусто
- [x] Регистрация → `POST /plugin/users` (`AuthService.registerNewUser`)
- [x] Смена пароля → `POST /plugin/users/:username/password` (`AuthService.setNewPassword`)
- [x] Last-seen → `POST /plugin/users/:username/last-seen` (`AuthListener.onQuit`)
- [x] Баланс/транзакции → `POST /plugin/users/:username/transactions` — хук
      в `UnityCommands.applyMoneyDelta(...)` (единственная точка, где реально
      меняется `Users.GeneralData.money`; через неё же идут и вызовы из
      `MoneyManager` — банк/АТМ, и из `ShopController` — покупки/продажи в
      магазинах-табличках, так что мирроринг покрывает оба источника разом).
- [x] **Job-queue для сайтовых денежных операций** (2026-08-03) — `/bank/transfer`,
      `/bank/invoices/:id/pay`, `/bank/salary/claim` на сайте раньше писали
      только в свою Postgres-бухгалтерию, реальные деньги не трогая (см.
      `updated/infra/game-integration-architecture.md`, раздел "Банк").
      Теперь: сайт создаёт `MoneyRequest(status=pending)` в Postgres и ждёт
      (до 8 сек) исполнения. `auth/MoneyRequestPoller.java` — новый класс,
      раз в ~2 сек (`GET /plugin/money-requests/pending`) забирает заявки,
      реально двигает деньги через `applyMoneyDelta` (списание у отправителя
      [+ комиссия при переводе не в свою страну], зачисление получателю),
      подтверждает через `POST /plugin/money-requests/:id/result`. Балансовый
      мирроринг для сайта происходит бесплатно как побочный эффект вызова
      `applyMoneyDelta` (см. пункт выше) — отдельно ничего дублировать не
      пришлось. Подтверждено вживую пользователем: `/ul money give` → реально
      меняет баланс → прилетает на сайт.
- [x] **`/ul money give <ник> <сумма>`** (2026-08-03) — OP-команда, идёт через
      тот же `applyMoneyDelta`. В плагине не было ни одной команды для выдачи
      денег без страны/зоны — это и обычная admin-утилита, и единственный
      способ протестировать мост без доступа к стране.
- [x] **`balance_sync`** (2026-08-03) — четвёртый вид заявки в той же очереди,
      без списания/зачисления: просто спрашивает у плагина реальный текущий
      баланс (`UnityCommands.getBalance`, новый метод — простое чтение без
      блокировки) и ставит `Account.balance` в точное соответствие (не дельта).
      Бэкенд дёргает эту заявку на каждый `GET /bank/balance` с коротким
      таймаутом (3 сек), откатываясь на закешированное значение, если плагин
      не ответил вовремя (например, игровой сервер сейчас не запущен). Нужно
      было, потому что событийный мирроринг сам себя не чинит: если
      какое-то событие потерялось (даунтайм, ручные QA-правки через API) —
      цифра на сайте расходится с реальной и виснет так навсегда, пока не
      случится следующее движение денег.
- [x] **Наигранное время** (2026-08-03) — `auth/PlaytimeReporter.java`, новый
      класс (в плагине раньше вообще не было живого трекинга — `StatsData.
      playtime`/`totalPlaytime` мёртвые поля из старой PHP-модели). Раз в 60
      сек считает прошедшее время для каждого аутентифицированного онлайн-
      игрока и шлёт дельту → `POST /plugin/users/:username/playtime`
      (эндпоинт уже был в backend, просто никто не вызывал). Плюс финальный
      репорт на выходе с сервера. Питает `/bank/salary` на сайте.
- [x] **Heatmap активности** (2026-08-03) — `chunkactivity/HeatmapReporter.java`,
      новый класс, раз в 5 мин. **Важно:** намеренно НЕ трогает
      `ChunkStats.playerActivity` (это поле питает биллинг зон через
      `ActivityWeights`/`ZoneActivityCalculations` — сбрасывать или менять
      его для отчётности нельзя, испортит реальные деньги за зоны). Вместо
      этого просто смотрит `ChunkStats.lastUpdated` — какие чанки трогали с
      прошлого отчёта — и шлёт по одной репрезентативной точке (центр чанка)
      на активный чанк → `POST /plugin/stats/activity`. Чисто наблюдение,
      без побочных эффектов на существующую систему. Питает `/stats` на сайте.

## Сделано (продолжение)

  сброс `dayDealCode`) и `UnityCommands.dayDealInfo/dayDealComplete`
  (проверка предмета в руке + реальная оплата через `applyMoneyDelta`) уже
  были рабочими. Не хватало только генерации самого дейлика — раньше это
  делал старый PHP-сайт (пул карточек, до 3 рероллов, подписанные payload'ы
  через браузер). Восстановлено на новом сайте: пул/реролл — чистое
  Postgres-состояние (ничего не двигает в игре, поэтому подписи через
  браузер не нужны — сервер сам всё помнит), а финальный подтверждённый
  выбор пишется в `Users.GeneralData.dayDealCode` через ту же
  money-request-очередь, новый `kind: "daydeal_confirm"`
  (`UnityCommands.setDayDealRaw`, новый метод). Формат строки на 100%
  совпадает с тем, что уже парсит `parseDayDeal` в плагине.

  не берётся и не должно. `POST /plugin/wiki/pages` в backend не наш случай,

Мирроринг/job-queue основа (auth, баланс, playtime, heatmap, дейлик) —

## Архитектурные решения по остальным разделам (не просто мирроринг)

Зоны, банк и апгрейды — во всех трёх случаях на сайте уже есть **независимая
параллельная система**, не то же самое, что «данные плагина, просто ещё не
запушены». Полный разбор по каждому разделу сайта (что с обеих сторон, где
конфликт, что рекомендую) — в `updated/infra/game-integration-architecture.md`
(репозиторий `farlandsconnect`). Коротко: помимо мирроринга (как auth) нужен
ещё один паттерн — **job-queue заявка** (сайт создаёт заявку → плагин
исполняет с реальной валидацией → пишет результат), для зон (инфраструктура
`zone_requests`/`ZoneManager.handle(...)` уже готова в этом репозитории, не
подключена к новому backend), апгрейдов и денежных переводов/наград с сайта.

Не начинать мостить зоны/банк/апгрейды без решения по этому документу.
